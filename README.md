# photo3d — 폰 사진·동영상으로 실측 3D 현장 모델 만들기 (건설안전 시뮬레이션용)

일반 스마트폰 사진 또는 동영상 → **m 단위 실측 3D 메쉬** → 유니티(크레인 시뮬레이션)로 반입.
DJI Terra · Metashape · Pix4D(엔젤스윙 계열)와 같은 원리(SfM + MVS 사진측량)를 오픈소스로 구성했다.

```
사진/동영상 ─▶ ① 입력정리 ─▶ ② SfM ─▶ ③ 축척·좌표정합 ─▶ ④ 조밀복원·메쉬·텍스처 ─▶ ⑤ 유니티 내보내기
              (블러 제거)    COLMAP     ArUco 마커 / GCP       OpenMVS                 GLB + 충돌메쉬
```

## 1. 왜 이 구성인가 (가우시안 스플래팅과의 관계)

| | 사진측량 (이 프로그램) | 가우시안 스플래팅 |
|---|---|---|
| 결과물 | 메쉬(면) — 충돌·거리 계산 가능 | 반투명 점 구름 — 보기에는 사실적 |
| 치수 정확도 | 마커/GCP로 cm 급 | 표면이 흐릿해 치수·충돌 판정에 부적합 |
| 유니티 물리 | MeshCollider 바로 사용 | 별도 메쉬 추출 필요 |
| 필요 자원 | CPU 로도 가능, GPU 면 빠름 | NVIDIA GPU 필수 |

크레인 안전(붐–건물 이격, 아웃트리거 지반)은 **정확한 면**이 필요하므로 사진측량이 본체다.
스플래팅은 같은 SfM 결과(`work/dense`)를 그대로 넣어 **보기용 레이어**로 추가할 수 있다(로드맵 4단계).

## 2. 정확도를 결정하는 요소와 대응

| 오차 원인 | 대응 (구현 위치) |
|---|---|
| 축척 미정 (사진만으론 크기를 모름) | 현장에 ArUco 마커를 깔고 모서리를 삼각측량해 축척 확정 (`scale.py`) |
| 기울어짐 | 바닥에 놓인 마커 전체로 수평면 추정 → Z-up |
| 현장 좌표 (도면/측량과 맞추기) | 마커 중심 측량좌표(GCP) 3점 이상 → 7-파라미터 정합 + 검사점 오차 보고 |
| 폰 렌즈 왜곡 | OPENCV 왜곡모델, 같은 폰 사진은 렌즈 1개로 묶어 공동 보정 (`sfm.py`) |
| 흔들린 사진 | 라플라시안 선명도로 자동 제외, 동영상은 구간별 최선명 프레임 (`frames.py`) |
| 검증 없는 결과 | 줄자 검증거리(`check.csv`) 오차, 등급 A/B/C/D 자동 판정 (`report.json`) |

## 3. 현장 촬영 가이드 (정확도의 절반은 촬영에서 결정)

**준비물**: A3 출력 ArUco 마커 5~8장(`tools/make_markers.py`), 줄자 또는 레이저 거리계.

1. 마커를 작업 영역 **둘레에 넓게** 깔고(최소 3장, 권장 5장 이상, 일부는 중앙) 평평하게 고정한다.
   - 인쇄 후 검은 테두리 한 변을 자로 재서 `--marker-size` 에 넣는다(예: 0.250).
   - **축척은 긴 거리로 잡는다**: 멀리 떨어진 마커 2쌍(10 m 이상) 중심 간 거리를 줄자/레이저로 재서
     `scale.csv` → `--scale-dist`. 마커 한 변(0.25~0.5 m)만으로 잡은 축척은 가상현장 검증에서 **2.2 % 오차**
     (10 m 에 22 cm)가 났다. 측량 가능하면 GCP(`--gcp`, 5점 이상 권장). 가상현장 2회 시험: 마커 크기만 1.8~2.2 %,
     줄자 긴 거리 1개 0.1 %(10 m 에 9.5 mm), GCP 3점 0.02~0.07 %. 줄자 거리 없이 마커 크기만 쓰면 등급 C.
   - 다른 1~2쌍은 `check.csv` 로 남겨 **독립 검증**한다(축척에 쓰지 않은 거리).
2. 폰 설정: **1x 기본 렌즈 고정**(줌·광각 전환 금지 — 아이폰 '매크로 자동 전환'·갤럭시 '장면 최적화'도 끔),
   초점·노출 고정(AE/AF 잠금), HDR·인물모드 끔.
   동영상은 **손떨림 보정(EIS/슈퍼 스테디) 끔** — 프레임마다 영상을 비틀어 렌즈 모델이 깨진다.
   **사진 우선**: 폰 동영상은 롤링셔터(한 프레임을 위→아래로 순차 촬영) 왜곡이 있어 빠르게 움직이면 수 cm 오차가 생긴다.
3. 촬영
   - 사진: 대상 둘레를 걸으며 **한두 걸음마다** 1장, 인접 사진끼리 **70~80% 겹치게**. 100~300장.
     (가상현장 시험: 같은 높이에서 22.5° 간격(반경 24 m 에서 9 m)으로 찍었더니 모델이 둘로 쪼개져 72장 중 31장만 복원)
   - 동영상: 4K 30fps, **천천히**(초당 0.5m 이하) 걷기. 빠른 회전 금지.
   - 같은 경로를 **높이를 바꿔 2~3바퀴**(눈높이, 팔 높이로 들기, 계단·옥상이 있으면 그곳에서).
   - 마커가 여러 사진에 보이도록 가끔 아래를 향해 찍는다.
4. 피해야 할 것: 역광, 유리·물 반사면 위주 구도, 사람·장비가 많이 움직이는 시간대, 하늘만 나오는 사진.
   움직이는 장비·사람이 많으면 `--masks` 로 가린다(<이미지명>.png, 검정=제외).

## 4. 사용법

```bash
# 사진 폴더
python -m photo3d run photos/ --marker-size 0.25 --check check.csv --out out/현장A
# 동영상 (여러 개 가능)
python -m photo3d run walk1.mp4 walk2.mp4 --marker-size 0.25 --out out/현장A --quality high
# 측량 좌표(GCP) 사용
python -m photo3d run photos/ --marker-size 0.25 --gcp gcp.csv --out out/현장A
```

`check.csv`: `id1,id2,거리m` · `gcp.csv`: `marker_id,x,y,z` (m, Z-up)

품질: `draft`(빠름) / `medium` / `high`(메쉬 정제 포함, 권장) / `ultra`(원본 해상도, GPU 권장)

**출력**

| 파일 | 용도 |
|---|---|
| `site_model.glb` | 유니티 보기용 텍스처 메쉬 (Y-up, 1unit=1m) |
| `site_collider.glb/.obj` | 유니티 충돌 판정용 경량 메쉬 |
| `site_model_zup.obj` | 라이노/CAD 확인용 (Z-up, m) |
| `report.json` | 등록률·재투영오차·마커 오차·검증거리 오차·등급 |
| `work/dense` | COLMAP 형식 — 가우시안 스플래팅 학습 입력으로 그대로 사용 가능 |

## 5. 설치

- **윈도우 + NVIDIA GPU (권장)**: `scripts/setup_windows.ps1` → `scripts/run_windows.ps1 영상.mp4 -MarkerSize 0.25 -Out out`
  (COLMAP CUDA 릴리스 + OpenMVS 릴리스 자동 설치, 특징점 추출·매칭이 GPU 로 수 배 빨라짐)
- **리눅스/클라우드 (CPU)**: `scripts/setup_linux.sh`

## 6. 유니티 연결 (`unity/`)

1. Package Manager → `com.unity.cloud.gltfast` 설치, `unity/` 폴더를 `Assets/Photo3D/` 로 복사
2. Tags and Layers 에 `Site` 레이어 추가
3. 메뉴 **Photo3D > Import Site Folder...** → 출력 폴더 선택 → 씬에 `Site_<이름>` 생성(충돌체 자동)
4. 크레인 프리팹에 `CraneClearanceMonitor` 추가, 붐 풋·붐 팁·후크·인양물 Transform 을 Segment 로 지정
   → 실시간 최소 이격거리, 경고(3m)/위험(1m) 단계, 이벤트(`OnLevelChanged`)
5. `OutriggerGroundCheck` 에 아웃트리거 패드 4개 지정 → 우클릭 "지반 판정 실행": 경사·높이차 판정

## 7. 실사 정확도 검증 (Strecha 벤치마크 — 실제 건물 DSLR 사진 + 레이저스캔 정합 정답 카메라)

`tools/eval_strecha.py` — 복원 카메라 중심을 정답에 7-파라미터 정합 후 잔차. CPU, SIFT, 순차 매핑.

| 장면 | 사진 | 범위 | 등록 | 형상오차 RMSE | 범위 대비 | 초점거리 오차 |
|---|---|---|---|---|---|---|
| fountain-P11 | 11 | 15 m | 11/11 | 4.4 mm | 1/3,400 | 0.03 % |
| Herz-Jesus-P8 | 8 | 17 m | 8/8 | 6.0 mm | 1/2,900 | 0.17 % |
| entry-P10 | 10 | 29 m | 10/10 | 9.3 mm | 1/3,100 | 0.24 % |
| Herz-Jesus-P25 | 25 | 32 m | 25/25 | 8.9 mm | 1/3,600 | 0.18 % |
| castle-P30 (마당 한 바퀴) | 30 | 45 m | 30/30 | 42.9 mm | 1/1,050 | 0.34 % |
| castle-P19 (마당 한 바퀴) | 19 | 45 m | 19/19 | 61.3 mm | 1/730 | 0.31 % |

**보정 실험 (채택 여부는 실사 결과로 결정)**

| 시도 | 결과 | 결정 |
|---|---|---|
| DSP-SIFT + 어파인 (`sift_hq`) | 6장면 중 3곳 개선·3곳 악화, 2~7배 느림 | 옵션만 |
| 전역 매핑 GLOMAP (castle-P30) | 42.9 → 41.0 mm | 옵션 (`--mapper global`) |
| RADIAL 렌즈 모델 | 42.9 → 95~133 mm | 불채택 |
| FULL_OPENCV 렌즈 모델 | 30장 중 4장만 등록 | 불채택 |
| 광학중심 보정 (`--refine-pp`) | fountain 4.4→3.1, castle-P30 42.9→40.5, entry 9.3→10.8, castle-P19 61→66 | 옵션만 |
| ALIKED+LightGlue | 클라우드 pycolmap 에 ONNX 없음 → GPU PC 의 COLMAP 4.x 에서 사용 | GPU 옵션 |
| 강건 모드 (인라이어 기준↑, DEGENSAC, 오등록 사진 자동 제외) | 실사 3장면 등록률 100% 유지·정확도 동등(8.7/43.6/65.9 mm), 반복벽돌 가상현장의 오등록(위치 수억 m로 튐) 제거 | **기본 켬** |

> 주의: 반복무늬(조적·거푸집·비계) 현장에서는 재투영오차가 0.3px 로 '좋아 보여도' 일부 사진이 엉뚱한 곳에
> 등록될 수 있다. 가상현장에서 실제로 발생했고 **마커 검사점 오차(6~17 cm)로만 드러났다** → 검사점/검증거리 필수.

결론: 30 m 이하 장면은 사진만으로 mm 급 형상. 건물을 한 바퀴 도는 45 m 장면은 누적 오차(드리프트) 4~6 cm 가
남고, 이는 렌즈 모델·특징점 조정으로 줄지 않는다 → **현장 마커(GCP)를 번들조정에 넣어 잡는다** (`--gcp`, 기본 GCP-BA).

### 적은 장수로 되나? (실사, 사진을 고르게 줄여 시험 — `eval_strecha.py --keep N`)

| 장면 | 장수 → 연결 / 오차 |
|---|---|
| 건물 한쪽 면 (15 m) | 11장 4.4 mm · 8장 4.4 mm · 6장 **3.7 mm** · 5장 4.9 mm · **4장 5.6 mm** · 3장 실패 |
| 마당 한 바퀴 (45 m) | 30장 42.9 mm · 20장 44.0 mm · **15장 전부 연결** 60.9 mm · 12장 10/12 · 8장 5/8 |

→ **한쪽 면 4~6장, 한 바퀴 15~20장**이면 된다(고르게 둘러 찍는 것이 장수보다 중요).
3장처럼 서로 멀리 떨어진 사진은 SIFT+COLMAP 의 한계 → GPU PC 의 MapAnything-apache 등으로 카메라를 구해
`--from-colmap` 으로 넘긴다(미검증). Teleport 도 실제로는 방 하나에 약 500장을 앱이 자동으로 찍는다(Varjo FAQ) —
현장에서는 **1~2분 동영상을 찍으며 걷기**가 가장 부담이 적다.

### 가상 건설현장 전 과정 검증 (`tools/eval_accuracy.py`, 정답 메쉬 대비)
폰 렌즈왜곡·노이즈·JPEG 를 입힌 120장, GCP 3점 + 번들조정, 품질 medium.

| 항목 | 결과 |
|---|---|
| 건물 길이 18 m / 폭 12 m | −20.9 mm (0.12 %) / −4.4 mm (0.04 %) |
| 슬래브 상단 높이 9.25 m / 컨테이너 높이 2.59 m | +48 mm / −34 mm |
| 10 m 검증거리 / 독립 검사점 | −5.3 mm / 38 mm |
| 표면 오차 중앙값 (건물 / 컨테이너) | 10.8 mm / 11.0 mm |
| 렌즈 자기보정 (초점거리) | 0.26 % |

한계: 눈높이 촬영이라 지붕·컨테이너 윗면은 비고(→ 높은 위치·드론 사진 추가), 지면 먼 곳에 떠다니는 노이즈가
있어 표면오차 꼬리(p90 0.4 m)가 길다. 120장 중 86장만 한 모델로 이어졌다(반복 벽돌 + 시험 시나리오 결함:
일부 근접 촬영 위치가 건물 안). 실제 현장 사진으로 재검증 필요.

### 빈 곳(지붕·윗면) 시험
| 방법 | 결과 |
|---|---|
| Poisson 으로 메우기 (`--fill`) | 구멍은 닫히나 형상을 '추정': 표면오차 중앙값 12→59 mm, 지붕이 2 m 이상 부풀고 면적 43 % 가 추정 → `site_estimated.glb` 로 분리, 유니티에서 '실측 아님' 경고 |
| 6 m 폴대 사진 24장 추가 | 19장 연결, 지면 복원율 7.5→18.5 %, 떠다니는 노이즈 제거(p90 434→70 mm) |
| 20 m 드론 사진 12장 추가 | **0장 연결** — 눈높이 사진과 시점·축척 차이가 너무 커서 매칭 실패 |
| 흰 콘크리트 지붕 슬래브 | 여전히 빔 — 무늬 없는 면은 사진측량이 못 잡음 |

→ 지붕 같은 핵심 면은 (1) 중간 높이 사진으로 단계적으로 이어 찍기, (2) 드론은 별도 비행으로 촬영 후
마커(GCP)로 같은 좌표에 합치기, (3) 무늬 없는 면은 마커·표식 부착, (4) 도면 기반 3D 와 결합으로 채운다.

OpenMVS v2.3.0 에서 발견해 우회한 버그: ① `formatTime` 버퍼 크기 오류로 DensifyPointCloud 강제종료 → 소스 패치,
② TextureMesh OBJ 저장 세그폴트 → PLY 로 저장 후 변환.
